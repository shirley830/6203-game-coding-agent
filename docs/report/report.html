1Summary

We built an autonomous coding agent that starts from a single, previously unseen game_design_prompt.md, writes a complete game into game/, and leaves a full execution record in traces/. The agent is started with one documented command and needs no human help afterwards. Its distinguishing design choice is that success is never declared by the language model: a deterministic controller grants success only when every mandatory acceptance criterion passes on the current code, with evidence, and those criteria are derived from the specification before any code exists and checked by actually playing the game in a headless browser.

2System architecture and rationale

The agent is a single sequential controller (Member 1) with five injected modules. Modules receive an immutable view of the run and return a typed proposal or observation; they cannot change controller state, call each other, or run tools themselves. Every file write, command and dependency installation passes through one tool gateway in the controller, which validates its scope, charges it to the budgets, records it in the trace and only then hands it to the runtime. All modules are wired by one production factory (agent/integrations.py); test doubles exist only under tests/.

ModuleContractResponsibility
Controller (M1)state machine, budgetsPhases, legal transitions, tool gateway, stopping conditions, the success gate
Planner (M2)create_plan, next_decisionPlan from frozen criteria; propose exactly one next action per call
Runtime (M3)executeFiles, commands, installs inside an OS sandbox; process-group cleanup; workspace revisions
Verifier (M4)prepare_acceptance, next_checkSpec-derived acceptance; read-only checks; browser play-testing; evidence
Recovery (M5)recommend_recoveryClassify each failure; recommend RETRY, REPAIR, REPLAN or ABORT
Tracing (M6)open_run, append_event, finalizeDurable events, checkpoints, evidence, run report, delivery check

Design rationale and trade-offs

  • One controller instead of a multi-agent system. A single owner of state makes every decision traceable and every budget enforceable, and it removes coordination failures between agents. The cost is less parallelism; for one game in a bounded time slot, predictability mattered more than throughput.
  • The model proposes, the controller decides. Language models are good at generating code and poor at judging their own completion. Success therefore requires a verification report that matches the current specification digest, workspace revision and acceptance-suite version, with evidence for every mandatory criterion.
  • Typed contracts first. The team agreed a written interface contract (docs/INTERFACES.md) before implementation, so six members could build modules in parallel and integrate them without changing each other's code.
  • Browser games by default. A self-contained HTML5 canvas game needs no build step or installation and can be verified by a real browser. The agent builds Python terminal or pygame games only when the specification asks for them, as the course allows both.
  • Provider independence. The model is reached through LiteLLM, so changing the course model from GLM-5.3 to Kimi K3 in October 2026 required only configuration and a reasoning cap (Sections 7.3 and 7.4).

3How the agent plans

Plan. After the acceptance suite is frozen (Section 4), the planner asks the model for 3-8 concrete tasks. Each task must reference acceptance criteria; the plan must cover every mandatory criterion and have an acyclic dependency graph, otherwise it is rejected and regenerated. The plan prompt treats the specification as data that cannot override system policy.

Decide, one action at a time. In the build loop the planner returns exactly one decision per call: a tool action (write, patch, read, inspect, run, install), a verification request with a launch command, or a plan revision. Because the controller exposes only the latest result, the planner keeps its own working memory: the files in game/ together with their current text (kept up to date across writes, reads and accepted patches), the last 25 actions and failures, guard notes, and facts from the start-up self-check (for example "node is not installed"). Showing the current code in every decision removed a costly pattern seen with Kimi K3: after a failed check the model re-read files one at a time, losing about 200 s of a 400 s run.

Write once, then patch. Each file is written in full once; later fixes are unified-diff patches that change only the affected lines, because model output is the slowest part of a run. Models often miscount hunk headers, so the runtime places a rejected hunk by its content (it must match exactly once); otherwise nothing is written. Step-by-step decisions use a lower reasoning cap (3 000 tokens) than planning and acceptance (8 000).

Guards. Some rules are enforced in code rather than trusted to the model:

  • A verification request is refused if the launch command refers to files that do not exist; game/README.md must contain the exact launch command and is written deterministically if missing.
  • After eight consecutive edits without verification, the planner requests verification itself. Live runs showed a model rewriting one file 35-45 times without fresh feedback until the time budget ran out.
  • The planner owns action IDs (models reuse example IDs) and repairs unambiguous format slips, such as {"decision": "read_file"} instead of a tool action of kind read_file. Calls use JSON mode.
  • Specification fidelity. The prompt forbids adding controls, shortcuts or behaviour outside the specification to make a check pass, and requires fixing the real defect instead (Section 4.4).
  • Presentation (Member 2). The first complete version must already be presentable (title, status bar, styled controls, clear win and loss messages), with all styling inline in index.html and every referenced file present. Visual polish never delays verification, because a passing verification ends the run.

4How the agent verifies its work

4.1 Acceptance is frozen before planning

Immediately after reading the specification, the verifier asks the model, in the role of an independent tester, for a state contract and 3-10 executable scenarios. The contract requires the game to expose its real live state as window.__gameState and a few setup hooks as window.__gameTest (for example placing a collectible next to the player). A scenario is a list of real inputs (key presses, held keys, clicks on DOM elements or grid cells) and JavaScript assertions over the state. These criteria are frozen with the generic launch, functional, interaction and technical criteria; neither planning nor repair can change them.

Model-written tests can be wrong, so each requirement is validated on its own: invalid steps, undeclared hooks, canvas clicks in a specification that explicitly requires the keyboard, or assertions that use undefined names (Member 4) drop that requirement only. The tester prompt also requires that a setup must not end the game before the expectation unless the ending is what is tested. If the reply is unusable, the verifier asks once more with the field errors; if fewer than three requirements survive, the generic criteria decide the run and an informational C-ACCEPTANCE-INCOMPLETE result keeps the gap visible. Such a run is never reported as full success (Section 4.3).

Disputed checks. A check can also look valid and still contradict the specification. In a Kimi K3 retest a minesweeper check placed the mines so that the first click flood-revealed the whole board and won, but expected the game to be still playing; the correct game failed it twice and the run spent its budget "repairing" it. A check is now disputed (test_conflict) when the planner returns dispute_check with the specification rule as evidence, or when the same check fails in exactly the same way before and after a game change. The acceptance model re-examines that one check: keep sends the planner back to fixing the game; replace substitutes a check of the same rule (same id and category, at least one expectation), and the unchanged game is verified again. Failed checks that end in exactly the same state, usually because they share one setup, are re-examined with it. Each check is re-examined at most once, with at most two disputes and four re-examined checks per run, the old and new versions are kept in the event log, and the original acceptance and specification are never edited.

4.2 The game is actually played

The harness starts the documented launch command, loads the page in headless Chromium and records JavaScript errors. It checks the contract on the live object, then runs every scenario on a freshly loaded page, saving a screenshot per scenario. A failing scenario reports the step that failed and the state after it, for example step 5 {"expect": "s.status === 'lost'"} … state after: {...}, which is exactly what the planner needs to repair the game. A generic interaction probe (keys, canvas points, board cells, buttons) and checks for a play surface complement the scenarios. Terminal and pygame games are verified in a process mode: start without a traceback, keep running, react to typed moves (pygame input can only be checked statically and is labelled as such).

4.3 The success gate

The controller computes the outcome; a verifier cannot simply claim success. A report passes only if its specification digest, workspace revision and acceptance-suite version are current, every criterion has a result, every mandatory result is PASS with non-empty evidence, at least one verification tool operation succeeded in this cycle, a launch command exists, and the trace is durably preserved.

The final output separates three result levels (Member 1), also stored in summary.json and run_report.md: launch (the page loaded), specific rules (how many spec-derived checks passed, and which were re-derived after a dispute) and delivery (game/ with README and launch command). Only when all three are complete is the run shown as fully accepted; a run that passed the generic checks alone is shown as acceptance incomplete. The levels do not change the outcome or the exit code.

5How the agent recovers from failure

Every failure is recorded with its phase and category and goes to the recovery module, which classifies it and recommends one of five decisions. The controller enforces the decision and all limits; modules cannot reset counters.

Failure classDecisionReasoning
Transient model error (timeout, connection, rate limit, 5xx)RETRYProposal-only calls are safe to repeat; waits 5 s, 15 s, 45 s, 60 s before each retry, within the deadline
Malformed model outputREPAIR / REPLANAsk again with the parse error visible; an invalid plan is regenerated
Command failed, file missingREPAIRInspect output and fix; never replay the unchanged command
Timeout or unknown side effectsREPAIRNever retried blindly; earlier verification is invalidated and the workspace re-inspected
Failed verificationREPAIR, periodically REPLANThe failing steps go to the planner; repeated failure rebuilds the plan
Broken test script (test_script_error on a mandatory check)ABORTThe test, not the game, is at fault; the game is never edited to satisfy it
Disputed check (test_conflict)REVISE_ACCEPTANCERe-examine that one check against the specification, then verify the unchanged game (Section 4.1)
Permission, sandbox or credential error; API key out of credit; process cleanup failureABORTRetrying cannot help; preserve artifacts and finalize honestly with a clear reason

Stopping conditions bound every run: total time (including a finalization reserve), steps, commands, retries per operation, global recovery attempts, and repeated no-progress cycles. Any stop still finalizes the trace and keeps game/. Before every verification the controller also snapshots the game source into the trace; if a run ends without success, it restores the version that passed the most mandatory criteria and records the decision. The outcome stays FAILED or EXHAUSTED: a better partial version never counts as success. Two later additions (Member 5): the same failure on an unchanged workspace triggers a replan after three occurrences and an abort after five, and a verifier fault (a broken test script on a mandatory criterion) aborts instead of "repairing" a game that is not at fault. In live runs this machinery handled real provider timeouts, malformed JSON (including empty {} replies from GLM-5.3, which the planner now absorbs without spending recovery attempts), runtime errors in generated code, and missing files.

6Runtime safety and tracing

Runtime (Member 3). Commands run as argument vectors (no shell) inside an OS sandbox (macOS sandbox-exec, Linux bwrap) that allows writes only to game/ and the run's private storage, so generated code cannot modify the agent, the specification or the traces. Each command runs in its own process group, which is terminated and confirmed gone after every command, timeout or cancellation. Dependencies install into an isolated environment. Credentials stay in the agent process: commands get a filtered environment and cannot read agent.env. A start-up self-check stops the run before game/ exists if Chromium, the sandbox, a free port or Python is missing; python -m agent.preflight --probe-model additionally makes one model call that must return valid JSON, so a wrong key, endpoint or reasoning setting is caught before the run.

Tracing (Member 6). Every controller event is appended to events.jsonl and is durable before the controller continues. The trace also holds checkpoints, every verification report, screenshots with a SHA-256 index, model usage per call (role, tokens, latency) and run_report.md, a readable timeline with each action's rationale, the frozen criteria, the plans and every verification cycle. finalize re-reads what it wrote before reporting the delivery as preserved, and python -m agent.delivery audits a finished trace, including run_report.md and every runtime output an action referenced against its archived copy and hash (Member 6).

8Current limitations

  • Model-written tests can be wrong. The scenarios come from the same model that writes the game. Filtering removes known bad patterns and a disputed check is re-examined once, but the re-examination is made by the same model, and a wrong test that a game happens to pass is not detected at all. Disputes therefore stay bounded and recorded, and every replacement must test the same rule.
  • Model speed decides many runs. Waiting for the model is most of a run, and its speed varies: the same minesweeper specification took 368 s, ran out of time, and took 165 s in three Kimi K3 rounds, and in the last retest a single decision took 204 s of a 400 s run; requesting the first verification without a model call and showing the time left brought the next seven runs to 76-360 s.
  • Real-time games are the weakest case. Scenarios assert on wall-clock behaviour, so timers and continuous scoring needed up to eight repair cycles, and the dodge and snake games exhausted their budget in several rehearsals. In the latest check all three passed, but two of their checks had to be re-derived because the game loop changed the state during the check.
  • Non-browser games are verified less deeply. Terminal games are played through standard input, but spec-derived scenarios apply to browser games only, and pygame input is checked statically.
  • Evaluation key and demo machine. All runs used team keys for the same models and provider; the evaluation key is issued before the presentation and checked with --probe-model, and the presentation machine still needs a full rehearsal.
  • Small evaluation. Fourteen specifications and at most three Kimi K3 runs per specification and agent version; results are indicative.
  • Platform. The command sandbox requires macOS or Linux with bubblewrap; there is no resume after a hard interruption.

9Next planned improvement

Deterministic time for real-time games. The two improvements planned earlier, keeping the best verified version and a model connectivity check, are now implemented (Sections 5 and 6). The remaining weak point is real-time games, whose scenarios currently race the game loop. The state contract will require a pause hook and a step(ms) hook that advances the simulation by a fixed amount, and the harness will run timing assertions on a paused game advanced step by step. Assertions such as "the score is still 0" or "an obstacle moves down" then become exact and repeatable instead of depending on frame timing, which targets the failure seen in the dodge rehearsal.

A smaller follow-up: standard setup hooks per game type (place an item next to the player, open a grid cell, set a score) to reduce unpassable model-written scenarios.

10Use of AI assistance

The team used Codex (OpenAI) and Claude Code (Anthropic) as coding assistants during development. They were used to integrate the members' branches and diagnose and fix cross-module defects found during testing (for example, the data mismatch between the verifier and runtime, the interaction check that failed to detect player movement, and macOS process-group cleanup issues). Members designed and implemented their own modules (see Section 11) and reviewed the integration changes affecting their modules before they were merged into the main branch; subsequent changes were made by Member 1 with the same assistance and are recorded in the Git history.

At run time the agent itself calls only the course-designated model through LiteLLM. It does not invoke any existing coding agent, and it contains no pre-written game code: every game is generated during the run, and a test enforces that the agent package ships no game files.
